# Architecture, module par module

Ce que fait chaque module de `src/`, et pourquoi il est ainsi.
Déplacé tel quel depuis `CLAUDE.md` le 2026-10-03 (le fichier, chargé à chaque séance, faisait 151 Ko). Rien n'a été résumé.

## Architecture

Deux couches sous `src/`, reliées par un orchestrateur (`game_operations`) et un bus de signaux Qt.

**Découpes du 2026-10-03** (méthodes et fonctions déplacées telles quelles ; l'ancien module RÉEXPORTE les noms, donc les imports existants marchent) :
- `src/core/catalogue_blocs.py` ← `game_data.py` (1 172 → 424 lignes) : validateurs (`_https_ou_rien`, `_JETON_SUR`, `_motif_sur`…), `_loc`, et les blocs `language_registry`, `language_files`, `controller_registry`, `saves`, `screenshots`, `trailers`, `contributors` avec leurs parseurs. `game_data` garde `GameVersion`, `GameData`, `Catalog`, `_parse_catalog`, `load_catalog`.
- `src/ui/stats_widgets.py` ← `stats_dialog.py` (1 062 → 484) : `_Etagere`, `_Mois`, `_Jauge`, `_CarteSauvegarde`, `_Scolarite`, `_Paragraphe` et les petites fonctions de format (`_minutes`, `_duree_courte`, `_hauteur_max`…).
- `src/ui/reglages_rubriques.py` ← `game_settings_dialog.py` (1 228 → 874) : classe parente `RubriquesDuJeu` (langue, touches, affichage verrouillé, manette, captures, fichiers) et les constantes de la fenêtre (`_LARGEUR`, `_COULEURS_COUT`…). Les effets d'image, préréglages et dépendances restent dans `game_settings_dialog`. **Un `monkeypatch` vise le module où la fonction est APPELÉE** : `open_local_path` des captures se patche dans `reglages_rubriques`.

### `src/core/` — logique métier (pas de widgets, sauf QThread/QObject/pyqtSignal)

- **`config.py`** — dataclass `Config`, sauvegarde JSON atomique (tmp+rename). `get_documents_dir()` passe par `SHGetFolderPathW` (OneDrive / Documents redirigés). Chemins différents en mode gelé (`sys._MEIPASS`). `APP_VERSION` vit ici, synchronisé avec `pyproject.toml`.
- **`game_data.py`** — dataclasses gelées du catalogue. `load_catalog()` fusionne `src/data/games.json` (embarqué) et `~/Games/AccioLauncher/_Launcher/catalog_cache.json` — **le plus grand `catalog_version` gagne (strictement)**. `GameData.from_dict` **valide les chemins `executable` au parsing** (refuse `..`, absolu, lettre de lecteur). **Le catalogue porte ses traductions** (bloc `i18n` par jeu et par version), résolues au parsing par `_loc()` : `set_language()` tourne avant `load_catalog()`, donc `game.name` est déjà traduit et aucun site d'affichage ne change. Raison : **le catalogue se met à jour à distance**, un jeu ajouté doit arriver traduit sans republier l'exe. `_loc` refuse une valeur qui changerait le TYPE d'un champ. Porte aussi `warning` (traduisible) et `warning_url` (**https uniquement, validé au parsing** — seule chaîne du catalogue qui atteigne le navigateur). Affichés par `ActionPanel._build_alerts` au dernier rang, en NOT_INSTALLED et INSTALLED. Remplissage i18n : `tools/apply_catalog_i18n.py` (idempotent).
- **`game_manager.py`** — possède `Config`, le catalogue, la carte des `GameState` et les empreintes SHA-256 (`set_asset_digests` / `expected_hashes`). `expected_hashes(version)` : catalogue (`sha256`/`sha256_parts`) d'abord, puis les empreintes publiées par GitHub ; `(None, [])` si rien → vérification sautée, jamais un échec. Recherche **insensible à la casse** du nom d'asset (cas réel : « hp6.7z.001 » vs « HP6.7z.001 ») ; une ambiguïté de casse est ignorée plutôt que devinée. Multi-parts : **tout ou rien**. `refresh_states()` re-détecte depuis le disque (après changement d'`install_path` ; préserve DOWNLOADING/INSTALLING). **`_backfill_missing_versions`** : un jeu INSTALLED sans entrée `installed_versions` reçoit la version recommandée, sinon `has_update` serait muet à vie. MàJ de jeux notifiées par `MainWindow._notify_game_updates` (recompte LOCAL + toast cliquable — le signal `update_counts` ne voit que le distant). Temps de jeu : `add_playtime` / `get_playtime` / `last_played` ; sessions < 10 s ignorées ; UNE ligne discrète dans `InfoPanel`, cachée si jamais joué.
- **`compat.py`** — **Linux : le « Windows » des jeux est un PRÉFIXE Wine.** Détection **`umu-run` puis `wine`** (`ACCIO_COMPAT=umu|wine` force ; GE-Proton installé préféré en `PROTONPATH`, puis un UMU-Proton déjà téléchargé — un chemin ABSOLU évite aussi qu'umu contacte GitHub pendant qu'une écriture de registre fait attendre la fenêtre). **Un préfixe PARTAGÉ par famille** (`_Launcher/prefixes/umu`, `…/wine`) : c'est le modèle que tout le code supposait déjà (un Documents, un AppData, un registre), le socle `vcredist_x86` des huit jeux ne s'installe qu'une fois, et Proton range le profil sous `steamuser` là où Wine prend le nom Unix — mélanger les deux sur un dossier rendrait les sauvegardes invisibles. **Chemins : l'hôte pour les FICHIERS, Windows pour les VALEURS** (`chemin_windows` : `C:\users\…` dans `drive_c`, `Z:\…` ailleurs, comparaison LEXICALE). Le registre du préfixe est du TEXTE (`system.reg`/`user.reg`) : **lu sans lancer Wine** (`lire_cle`, échappements `\xHHHH` relevés sur un vrai préfixe). `environnement_hote` restaure `LD_LIBRARY_PATH` (le chargeur PyInstaller l'a modifié) pour tout enfant — `LD_LIBRARY_PATH_ORIG` s'il existe, sinon on ne retire QUE nos entrées (`_dans_le_dossier`, par COMPOSANTS : `/tmp/_MEIabc` n'est pas sous `/tmp/_MEI`) ; **`assainir_environnement()`** l'applique au processus lui-même (`main.py`, exe gelé Linux) pour ce que Qt lance sans nous (`xdg-open`, le navigateur) — la glibc a déjà lu la valeur au démarrage, le launcher n'en dépend plus. `processus_du_jeu` = `tasklist` sous `/proc` (Wine nomme le processus d'après l'exe Windows, VÉRIFIÉ). Tout se résout À L'APPEL depuis `config.CONFIG_FILE_PATH` ; **Runtime d'umu : vérifié au plus une fois par semaine** (`mise_a_jour_runtime_permise`, marque `_Launcher/umu-runtime-verifie`, sinon `UMU_RUNTIME_UPDATE=0`) — le CDN de Valve sert un `VERSION.txt` incohérent et umu retéléchargeait 195 Mo avant CHAQUE partie (17 s au lieu de 4,5, jusqu'à 59 s). Un processus que la fenêtre ATTEND (`regedit`) passe `environnement(…, mise_a_jour_runtime=False)`, qui ne consomme pas la semaine : demandée puis refusée derrière, elle sautait sept jours (revue du 2026-09-30). `encodage_ansi` est mémoïsé sur date+taille de `system.reg` (186 ms par patch d'INI). `chemin_windows` retente en chemins RÉSOLUS (`/home` → `/var/home` sur Silverblue). `lanceur()` est mémoïsé, `oublier()` refait la détection (appelé par `invalidate_vcredist_cache` et au clic sur JOUER).
- **`preparation_wine.py`** (QThread) + **`ui/preparateur_wine.py`** — crée le préfixe (`umu-run ""` / `wine wineboot --init`, Mono et Gecko écartés) puis installe les verbes winetricks (`umu-run winetricks` ajoute `-q` lui-même). **Jamais d'elle-même : sur un clic**, après un dialogue qui dit ce qui sera téléchargé (Microsoft, Proton). Journal `_Launcher/logs/wine-preparation.log`. Nouvelle session de processus : l'annulation (fermeture) arrête tout le GROUPE. Un code non nul de la création ne prouve pas l'échec (`umu-run ""` en rend un) : on attend `system.reg`, 10 s au lieu de 90. Échec des composants → « Lancer quand même » (`launch_game(ignorer_prerequis=True)`) : les composants intégrés à Wine suffisent parfois.
- **`composants_windows.py`** (QThread) + **`ui/installateur_composants.py`** — le pendant WINDOWS (ACT-054, 2026-10-08) : tous les composants manquants d'un clic. **Même contrat que `PreparateurWine`** (signaux `message`/`commencee`/`progression`/`terminee`, `demarrer`/`annuler`/`shutdown`) : `GameDetailView._wine` est l'un ou l'autre selon `composants_windows.disponible()`, la barre du bas et les handlers n'en savent rien. Installeurs pris chez Microsoft (`PAQUETS`, adresses relevées le 2026-10-07, toutes signées), **signature Authenticode vérifiée** (`Valid` + `O=Microsoft Corporation`, chemin passé à PowerShell par l'ENVIRONNEMENT) : un fichier qui ne passe pas n'est jamais exécuté. Tous lancés par UN `.bat` derrière UNE invite (`ShellExecuteExW` runas, attente interruptible), dans un `mkdtemp` (règle 70), **aucun chemin dans le corps** : `%~dp0` (règle 79). La RELECTURE (`prerequis_manquants`) fait foi, pas les codes. Refus de l'invite → toast (règle 69) ; signature, téléchargement, composant encore absent → boîte avec « Ouvrir la page Microsoft ». `conftest` interdit `executer_eleve` à tous les tests. **Options silencieuses jamais vues sur un Windows où les composants manquent** : à valider avant de s'y fier.
- **`game_registry.py`** — lecture/écriture des valeurs de registre d'un jeu. Trois contraintes relevées sur une vraie installation : **vue 32 bits** (`KEY_WOW64_32KEY`), **valeurs nommées ET typées** (`Language` en REG_SZ, `1.0\\Language` en REG_DWORD), **HKLM exige l'élévation** — d'où : on lit (gratuit), on compare, on n'écrit que si ça diffère. L'écriture élevée passe par un `.reg` UTF-16 + `regedit /s` dans un **dossier temporaire à nom aléatoire** (`mkdtemp` — un chemin fixe laissait remplacer le fichier avant son import ADMINISTRATEUR), **et on relit derrière** (`regedit /s` est muet même en échec). `refus_de_cle` / `refus_de_valeur` sont PURES et forment la seule barrière entre le catalogue distant et le registre. **`comparer(...)` rend `{nom: (actuel, voulu)}`** : `ecrire_valeurs` passe ces écarts au rappel, qui affiche « remplace : … ». Sur une machine où EA a installé le jeu, `Locale` et `Install Dir` sont DÉJÀ posés ailleurs — le cas normal est un remplacement. **`ecrire_valeurs(..., confirmer=…)`** prévient JUSTE AVANT d'écrire et seulement s'il y a une écriture : sous HKLM ça enchaîne sur UAC, et une autorisation qui surgit sans raison connue se refuse. Comme le rappel ne part qu'en cas d'écart réel, prévenir TOUJOURS ne devient jamais un nag. **`launch_game(..., avertir=…)`** signale une écriture nécessaire qui n'a pas abouti : le lancement continue, mais l'appelant DOIT distinguer l'échec du refus délibéré (`on_play` retient `accepte`). **`disponible()`** dit si ce système a un registre atteignable — sous Linux, un lanceur ET un préfixe initialisé (avant, écrire lancerait umu pendant que la fenêtre attend). **Sous Linux, `_ecrire_eleve` = `_ecrire_par_wine`** : le même `.reg` (même `construire_reg`, même barrière) posé dans `drive_c/windows/temp` et importé par `regedit /S` via le lanceur, puis RELU (le `system.reg` n'arrive qu'à l'arrêt du wineserver : 20 s d'attente max, VÉRIFIÉ à 3 s sous Wine 9.0). Pas d'UAC, mais la prévenance reste et son texte le dit ; `HKCU\Software` n'est pas redirigé en vue 32 bits.

  **Ce que lisent réellement HP7 parties 1 et 2** (relevé dans `hp7.exe` / `hp8.exe`, pas deviné) : les deux lisent **`Locale`** et **`Install Dir`**, **jamais `Language`**, contrairement à ce qu'écrit l'installeur EA. Les valeurs acceptées **DIFFÈRENT** : partie 1 `en_UK fr_FR it de es pl ru`, partie 2 `en fr it de es pl ru`. C'est ce qui explique la contradiction entre les guides (« `fr` ») et le registre d'une vraie machine (« `fr_FR` ») : les deux avaient raison, pour des parties différentes.
- **`reglages_correctif.py`** (pur) — réglages du correctif PC de HP4-HP6, écrits dans son `d3d9.ini` à côté de l'exe. **Seulement ce qui a été VU en jeu** : le catalogue les déclare par jeu (`fix_settings`), un identifiant inconnu est ignoré. **Seulement le nouveau correctif** : reconnu à `[Accio.Window]` ; sur l'ancien wrapper (celui des archives publiées), la fenêtre dit que les réglages arrivent avec la prochaine version au lieu d'écrire des clés que personne ne lit. **Édition en place** (seule la ligne change, CRLF et encodage gardés, écriture atomique). Le préréglage de touches se calcule depuis la **disposition du clavier** (codes de balayage → lettres : ZQSD en AZERTY, WASD en QWERTY) — le correctif lit les touches par leur nom IMPRIMÉ ; hors Windows, WASD. Des touches posées à la main ne sont jamais écrasées. Affiché par `GameSettingsDialog._section_correctif`, écrit AUSSITÔT (pas de bouton « Appliquer »), échec → contrôle remis sur le fichier + message.
- **`touches_correctif.py`** (pur) + **`ui/editeur_touches.py`** — l'éditeur de touches de HP4 (2026-09-30), sous le préréglage ZQSD dans l'onglet Commandes, affiché quand le jeu déclare `touches_zqsd` : les 11 actions de `kActionsHp4` (keys.cpp), un clic puis la touche ou le bouton de souris, écrit AUSSITÔT (Échap annule). Les noms sont ceux que lit le correctif (lettres telles qu'IMPRIMÉES, `LShift`, `Num7`, `MouseLeft`… ; « , » « ; » et tout non-ASCII refusés). **Une touche donnée à une action perd son rôle d'origine** (g_consumed) : `sans_touche` le calcule par POSITION (VkKeyScan sous Windows, US ailleurs) et l'éditeur l'écrit (« Extremos n'a plus de touche : S sert maintenant à Reculer »). Une touche n'a qu'une action (`attribuer` la retire aux autres). Le préréglage se verrouille dès qu'une de SES huit touches est choisie à l'unité, et « Remettre toutes les touches du jeu » le libère ; la remise à l'origine couvre les onze actions (`_cles`). Gauche/droite par le code de balayage natif (Windows 0x36/0x11D/0x138, X11 62/105/108) ; pavé numérique verrouillage éteint → `Num8`, pas `Up`.
- **`game_language.py`** — langue d'un jeu, extrait de `game_manager` (763 → 639 lignes). Les fonctions prennent `game` et `config` EXPLICITEMENT au lieu de lire `self`, donc s'exercent sans construire de manager. `langues_disponibles(game)` filtre sur la PRÉSENCE du fichier témoin (`requires_file`) : le registre ne fait que SÉLECTIONNER, les fichiers viennent du disque d'origine — HP7 partie 1 n'embarque que `DH1_French.pck`, la partie 2 les sept. **`valeurs_registre(game, code)`** compose les valeurs COMMUNES du bloc (`values`, `%INSTALL_DIR%` substitué) **plus** celles de la langue, langue en dernier : une seule écriture, donc **une seule invite UAC** au lieu de deux à la suite. `apply_game_language` applique AVANT de persister, sinon un UAC refusé laisserait en config un choix que le registre n'a pas pris. Les tests bouchonnent `src.core.game_language.registre.*`.
- **`pre_launch.py`** — fonctions pures de pré-lancement UE1 (substitution, patches INI, création/suppression de fichiers, déblocage DLL). **`substituer_pour_le_jeu`** = `substitute_vars` pour une VALEUR que le jeu lira (INI, `Install Dir`) : identique sous Windows, chemin Windows (`C:\…`/`Z:\…`) sous Wine — `SavePath=/home/…` ne tombait juste que si le lecteur courant était `Z:`. Sous Linux, les INI suivent la page ANSI du PRÉFIXE (`_encodage_ini`, valeur `ACP` de son registre ; repli cp1252). **`restaurer_configs_manquantes`** recopie une config livrée qui a DISPARU de Documents, avant les patchs (règle plus bas). **`env_de_lancement(dpi_aware)`** ajoute `__COMPAT_LAYER=HighDpiAware` sous Windows **pour un jeu qui le déclare au catalogue**, `None` sinon (ce que `Popen(env=None)` attend). **Deux jeux sur huit le déclarent** (HP7a/HP7b) — consigne explicite : eux seuls posaient le problème, les six autres n'ont pas été mesurés. La variable ne persiste RIEN (portée au processus), là où l'onglet Compatibilité est indexé par CHEMIN COMPLET.
- **`downloader.py`** — `QThread` sur httpx en streaming (**httpx importé paresseusement dans les méthodes**, test AST de régression). HTTPS only, multi-part avec reprise. **Plafond d'octets** = `expected_size_mb × 1.5` (`SIZE_OVERHEAD_FACTOR`) ; `0` le désactive. **SHA-256 incrémental pendant le stream** (plus d'UI figée à 100 %) ; `_verify_sha256` ne sert plus qu'aux parts déjà en cache ; mismatch → suppression + réessai. **Boucle d'écriture UNIQUE** (`_ecrire_chunks`, `_refuser_taille_annoncee`) : elle existait en deux exemplaires (nominal et reprise HTTP 416), le second sans aucun test. `TestReprise416` prouve la reprise par la SÉQUENCE des requêtes (une avec `Range`, puis une sans).
- **`self_update.py`** — auto-update en un clic (Windows gelé) : `.bat` attend la mort du processus, remplace l'exe, relance. `can_self_update()` garde le chemin : exe gelé ET dossier où l'on peut créer un fichier (sonde réelle, `os.access` mentant sous Windows ; ACT-004). `UpdateDispatcher.can_install_itself` exige en plus une empreinte publiée par GitHub, sinon page de release et raison au journal (ACT-008). **`relaunch_after_exit()`** réutilisé par « Redémarrer maintenant » et le dialogue de plantage. **Le `.bat` s'écrit avec `newline=""`** (sinon `\r\r\n` → cmd coincé dans `:wait`), se lance avec `CREATE_NO_WINDOW` + DEVNULL, **jamais `DETACHED_PROCESS`** (qui bloque `tasklist | find`), et **avec `env=_clean_pyinstaller_env()`** : sans purge des `_PYI_*` (+ `PYINSTALLER_RESET_ENVIRONMENT=1`), l'exe onefile relancé se croit enfant de l'instance morte et crashe « Failed to load Python DLL ». Voir pyqt-pitfalls #18 et #20. **Le remplacement de l'exe est RÉESSAYÉ (~30 s, `_CORPS_REMPLACEMENT`)** : un onefile PyInstaller, c'est DEUX processus, et `:wait` n'attend que l'enfant Python ; le bootloader, qui tient l'image de l'exe, vit encore 340 à 390 ms (mesuré, 5 refus sur 5 d'un remplacement immédiat). Le `move` unique échouait en silence, l'ANCIEN exe était relancé et reproposait la mise à jour (joueur, 1.0.4 → 1.0.6). Corollaire : une version ne corrige que les mises à jour qu'ELLE fera — les installations ≤ 1.0.6 gardent l'ancien script. **Linux (AppImage)** : `appimage_courante()` lit **`$APPIMAGE`, jamais `sys.executable`** (il vit dans un montage qui disparaît avec le processus) ; `can_self_update` exige aussi un dossier inscriptible (sinon page de release, plutôt qu'un échec APRÈS le téléchargement). `_remplacer_l_appimage` remplace **tout de suite** et atomiquement (copie à côté de la cible — même volume —, `chmod 755`, `os.replace`) : l'instance qui tourne garde l'ancien fichier monté. La relance passe par **`_relancer_apres_la_fin`** : un `/bin/sh` détaché (nouvelle session) qui **attend la mort du PID** puis `exec`. L'ancienne relance IMMÉDIATE butait sur l'instance unique : « Redémarrer maintenant » fermait sans rouvrir. PID et commande par l'environnement et `"$@"`, jamais dans le corps du script (même principe que les `%ACCIO_*%`). `nom_du_telechargement(version)` : `.exe` ou `.AppImage`.
- **`installer.py`** — orchestrateur `QThread` mince (extraction → déblocage → config_files → nettoyage). Délègue à `extractors.py` et `post_install.py`.
- **`extractors.py`** — extraction pure avec protection Zip Slip : `extract_7z` (**7z.exe bundlé, unique extracteur 7z** — progression fine, annulation immédiate, multi-volume `.7z.001` natif ; py7zr retiré), `extract_zip`. **Linux : `assets/7z/linux/7zzs`** (7-Zip officiel, variante STATIQUE — aucune dépendance au système), puis `7zz`/`7z`/`7za` du système par chemin absolu ; chaque build n'embarque que le sien (`_keep` du spec). **Sa progression s'efface à coups de RETOURS ARRIÈRE (`\x08`), sans aucun `\r`** : lue par lignes, elle n'arrivait qu'à la fin — `_segments_de_progression` découpe sur `\r`, `\n` et `\x08` (contre-épreuve dans `TestProgressionDu7ZipLinux`). **`verify_extracted_paths` ne parcourt que les dossiers de premier niveau de l'archive** (`premiers_niveaux`) : la destination contient `_Launcher/` et le préfixe Wine, dont `dosdevices/z:` → `/` faisait refuser TOUTE installation une fois Wine préparé (HP2, 2026-09-30). Les multi-parts émettent le `.001` brut (pas de concaténation) ; `Installer._delete_archive` retire tous les volumes.
- **`chemins.py`** — **la seule barrière « chemin relatif sûr »** (`refus_de_chemin`, `chemin_relatif_sur`, `est_peripherique`), appelée par l'exécutable du catalogue (`game_data`), les blocs (`catalogue_blocs`), le manager et les entrées d'archive (`extractors.is_unsafe_entry`). Il y en avait QUATRE, qui ne refusaient pas la même chose (octet nul et longueur d'un côté, « .. » maquillé d'un autre, CON/NUL d'un troisième) ; celle-ci refuse l'union (audit du 2026-10-07, ACT-007). Vérifiée avant branchement : aucun des 2 086 fichiers des jeux installés ni aucun chemin du catalogue ne change de verdict. `test_fuzz.TestCheminUnique` refuse qu'un module se refasse la sienne. **Ne pas y ajouter de refus sans repasser les fichiers réels** : une entrée d'archive refusée bloque toute l'installation.
- **`fichiers_essentiels.py`** (+ la boîte **`ui/fichiers_manquants.py`**, qui porte aussi `ouvrir_dossier_du_jeu`, sorti de `game_detail_handlers` pour son plafond de lignes) — l'exécutable et les fichiers `essential_files` du catalogue sont-ils encore là ? Présence seule, casse ignorée. Appelé par « Vérifier / réparer les fichiers » (avant la question de configuration ; « sont tous là » n'est dit que si le catalogue a une liste) et après un lancement raté (`proposer_apres_plantage`, `signaler_arret`), **jamais avant de lancer** (un mod ne doit rien bloquer). Détail du champ dans CATALOGUE_ET_JEUX.md.
- **`post_install.py`** — `unblock_extracted`, `apply_config_files` (avec sauvegarde `.bak`), **`ranger_dans_sous_dossier`** (voir « Le sous-dossier `pc` de HP7 »). `apply_registry` **a été supprimé** avec toute la plomberie `registry` : un bloc `registry` dans `games.json` est désormais simplement IGNORÉ, ce qui est franc — avant, il était accepté au parsing puis échouait **en silence**.
- **`trailers.py`** — bandes-annonces, **hors de l'exécutable**. Deux vidéos faisaient passer l'exe de **74 à 160 Mo** ; les huit l'auraient mené au-delà de 500, pour un ornement facultatif. Publiées en assets de release (`trailers-v1`), déclarées par le bloc `trailers`, téléchargées à la demande. Module PUR : `chemin_local`, `present`, `manquantes`, `fichiers_perimes`, `supprimer_tout`, `chemin_a_jouer`. **Le fichier LOCAL porte la version** (`hp1_video_v1.0.mp4`) alors que l'asset non : sans ça, améliorer une bande-annonce ne remplacerait jamais l'ancienne. Corollaire obligatoire : `fichiers_perimes` fait le ménage AVANT chaque téléchargement (sinon le poids double à chaque révision), et **seulement** sur le motif `<id>_video_v<version>.mp4` — le dossier appartient à l'utilisateur.
- **`thread_utils.py`** — **`arreter_a_la_fermeture(thread, nom)`**, geste d'extinction partagé par `GameOperations.cancel_all` et `UpdateDispatcher.shutdown`. En session un thread récalcitrant se GARE (`_zombies`) ; à la fermeture, non — Qt le détruit avec son parent, ce qui **abandonne le processus** (`0xC0000409`, sans message ni rapport). Attendre plus est exclu (`read` httpx à 120 s), d'où `terminate()` + `wait()`. ### Journal, sortie et CI

**`main.py`** configure le logging rotatif, l'exception de haut niveau, `install_excepthook()` et le splash avant `MainWindow`. Fichier en **INFO dans l'exe**, DEBUG depuis les sources, `ACCIO_JOURNAL=debug` pour rendre le détail à l'exe. Sous Linux : `assainir_environnement()` avant `QApplication`, et **`setDesktopFileName(DESKTOP_ID)`** (`be.acciolauncher.AccioLauncher`) — l'équivalent de l'AppUserModelID : sous Wayland, `setWindowIcon` est ignoré, c'est cet `app_id` qui relie la fenêtre à son `.desktop`, donc à son icône.

**`main()` sort par `os._exit(code)` après `logging.shutdown()`**, jamais par `sys.exit(app.exec())` : pendant la finalisation de l'interpréteur, sip détruisait les objets C++ dans le désordre — violation d'accès dans `sip.cp314-win_amd64.pyd` à **2 fermetures sur 8**, et 5 fois au journal Windows ; **0 sur 14** après. `PyQt6.sip` n'a plus `setdestroyonexit`. Tout ce qui doit être écrit l'est dans `closeEvent`.

**Paquets CI figés avec empreintes** (`.github/requirements/*.txt`, `--require-hashes`) : un `tests.txt` résolu en `--universal` couvre Windows 3.12/3.14 et Linux ; `build.bat` n'en dépend pas. **CodeQL** tourne en workflow (Scorecard ne reconnaît pas le « default setup », ni Bandit, comme SAST ; les deux ne peuvent coexister). **Fuzzing** (`fuzz.yml`, Atheris, Linux) : `fuzz/invariants.py` écrit en assertions ce que promettent les barrières entre le catalogue DISTANT et la machine ; `tests/test_fuzz.py` les rejoue sous Windows. Il a trouvé `"year": 1e999`, les séparateurs de ligne Unicode dans un `.reg`, et des noms d'archive que les deux gardes Zip Slip jugeaient différemment.

**`tests.yml`** — pytest sur `windows-latest` en **3.12 ET 3.14** (3.12 est le plancher déclaré et n'avait jamais été testé : `Path.read_text(newline=…)`, apparu en 3.13, y cassait `tools/sync_trailers.py`) + smoke `ubuntu-24.04` offscreen, **bloquant**. Ce job fut rouge à CHAQUE run depuis sa création : ne bloquant rien, personne ne le regardait. Remis au vert, **puis rouge de nouveau quatre semaines** pour la même raison — 25 tests de LANGUE DE JEU supposaient un registre Windows sans le dire. Remède : la fixture **`registre_atteignable`**, à demander pour tout nouveau test de langue de jeu. **Tant qu'un job n'est pas bloquant, un rouge y dure des semaines. Ne pas remettre `continue-on-error`.** Pour reproduire : `python:3.14-slim` + les bibliothèques Qt du workflow **+ `libgssapi-krb5-2`** (QtNetwork la réclame) **+ `fontconfig fonts-dejavu-core fonts-liberation`** — sans le paquet `fontconfig`, la bibliothèque est là mais ne trouve aucune police, ce qui fait un troisième environnement. **+ `libglib2.0-0t64`** (le runner Ubuntu l'a d'office, pas l'image : `conftest` s'arrête sur `libglib-2.0.so.0`), et **lancer pytest sous un utilisateur NORMAL** (`useradd`, `su`) : en root, un fichier en lecture seule reste inscriptible et `test_l_attribut_de_l_archive_est_conserve` échoue pour rien. Rouge du 2026-09-27 (cinq commits) : un test de captures attendait le chemin de l'hôte là où Linux écrit `Z:\…` — **un test qui écrit un chemin pour le JEU passe par `chemin_pour_le_jeu`**.

**Releases construites par la CI** (`release.yml`). **Tout se fait depuis le site GitHub** : Actions → release → Run workflow, case « Créer la release » cochée. Le tag se DÉDUIT d'`APP_VERSION` (refus hors de `main` ou si la version a déjà un tag) et naît sur le commit construit (`--target`) — **pas de déclenchement sur tag**, publier le brouillon en créant un relancerait un build voué à l'échec. **Trois jobs** : `version` (le tag, calculé UNE fois), `windows` (`build.bat`) et `linux` (`build.sh`, **`ubuntu-22.04`** : une AppImage exige la glibc de sa machine de build ; tous les autres jobs Linux des workflows sont figés en `ubuntu-24.04`, jamais `ubuntu-latest`, qui passe à Ubuntu 26 le 2026-10-19) en parallèle, puis `brouillon`, qui n'existe que si les DEUX ont réussi — tout ou rien. Attestation de provenance Sigstore sur CHAQUE binaire (et son `.sigstore.json` joint), UNE release en **BROUILLON** portant les quatre fichiers, notes pré-remplies depuis `.github/release-notes.md`. Rien n'est public avant « Publish release », et l'auto-update ne voit pas un brouillon. Case décochée = build d'essai. `build.bat` le permet par `CI` et `ACCIO_PY`. **Toutes les actions épinglées par empreinte de commit**, Dependabot tient les deux à jour. `LICENSE` ne contient QUE le texte GPL v3 officiel (sinon GitHub affiche « Other ») : les termes additionnels de l'article 7 vivent dans `ADDITIONAL-TERMS.md`. **Licence : GPL-3.0-only depuis le 2026-09-24** (MIT jusqu'à la 1.0.6) — la plus stricte que permet PyQt6 ; interdire la redistribution exigerait PySide6 ou une licence Riverbank.

**AppImage** (`build/linux/`). Le spec produit un DOSSIER sous Linux (onedir : un onefile dans une AppImage se décompresserait en plus dans /tmp à chaque démarrage), que `appimage.py` range dans `AccioLauncher.AppDir` (`usr/lib/AccioLauncher`, `AppRun` en sh, `.desktop`, icônes EXTRAITES telles quelles des sept tailles de l'`.ico`, licence et avis tiers dans `usr/share/doc`). **appimagetool 1.9.1 et le runtime `type2-runtime` 20251108 sont épinglés par version ET empreinte** (jamais `continuous`) ; le runtime est statique, donc **pas de libfuse2** requise — absente de Fedora, donc de Bazzite. **Le nom ne porte pas la version** (`AccioLauncher-x86_64.AppImage`) : l'auto-mise à jour remplace le fichier sur place, et `updater.asset_de_la_plateforme` le reconnaît à son architecture. Relevés sous Xvfb sur l'AppImage elle-même : `WM_CLASS` = `AccioLauncher` (d'où `StartupWMClass`), journal « (AppImage) », et le chargeur PyInstaller onedir place `_internal` en tête de `LD_LIBRARY_PATH` sans créer `LD_LIBRARY_PATH_ORIG` s'il n'y avait rien — les deux cas de `compat.environnement_hote`, vérifiés sur un enfant réel. 62 Mo (l'exe : 42), **grâce à `strip=True` sous Linux** : le Python d'`actions/setup-python` garde ses symboles de débogage (`libpython` : 33 Mo, 7 épurée), et le build d'essai de la release sortait 77 Mo là où le poste en faisait 62 — le contenu d'un build ne dépend pas de la machine qui le fait (règle 94).
